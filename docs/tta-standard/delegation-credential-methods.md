# 권한위임장 4가지 발급 방식 — 예시 및 설명 (백데이터)

*(표준초안 §5.2 「위임장 발급 모듈」 보충 자료 — 심의·설명용. 표준 본문에는 포함하지 않는 배경 자료이다.)*

권한위임장(delegation credential)은 네 가지 형태 중 **하나**로 발급된다. 네 가지를 모두 사용하는 것이 아니며, 서비스·구현 환경에 따라 하나를 택한다. 본 자료는 각 방식을 동일한 예시 시나리오로 설명한다.

## 공통 전제 (§5.1 위임 등록 — 모든 방식의 선행 단계)

사용자 **Alice**가 에이전트 **Bob**에게 "쇼핑몰 결제, 월 10만원 한도" 권한을 위임한다고 하자. 어느 방식이든 **먼저 권한위임정보가 온체인 위임 레지스트리에 등록**된다.

```
블록체인 (온체인)
└ 위임 레지스트리 = DelegationRegistry 스마트 컨트랙트 (주소 0xREG…)
    └ storage:  위임ID  →  권한위임정보 { 위임자:Alice, 에이전트:Bob, 권한범위:결제,
                                          한도:10만원/월, 유효기간:~2026-12-31, 철회:false }
```

- 「위임 레지스트리」(§3.6)는 별도 저장 공간이 아니라 **이 스마트 컨트랙트 자체**이다.
- `register()`로 권한위임정보를 등록하면 **위임 ID**(= 사용자·에이전트·논스의 해시, 예: `0xD1…`)로 인덱싱되어 storage에 저장된다.
- **위임 ID는 이 온체인 정보를 가리키는 열쇠이며, 네 가지 방식이 모두 공유한다.**

네 가지의 차이는 "Bob에게 어떤 형태의 **증표(위임장)**를 주느냐"이다.

## 1. VC 방식 (§5.2.1)

Alice의 DID로 **서명한 검증 가능한 자격증명(VC)** 을 발급한다.

```json
{ "type": "DelegationCredential",
  "issuer": "did:meta:Alice",
  "credentialSubject": { "agent":"did:meta:Bob", "delegationId":"0xD1", "scope":"결제" },
  "proof": { Alice의 전자서명 } }
```

- Bob이 서비스 요청 시 이 VC를 서비스 제공자에게 제시.
- 검증: ① Alice DID 공개키(DID 레지스트리에서 획득)로 **VC 서명 검증**(진짜 Alice가 위임했는가) → ② 위임 ID `0xD1`로 **온체인 조회**(한도·유효기간·철회 여부 확인).

## 2. 스마트 컨트랙트 어드레스 방식 (§5.2.2)

증표 자체가 **(레지스트리 컨트랙트 어드레스 + 위임 ID)** 참조이다.

```
위임장 = 0xREG…  /  위임ID 0xD1
```

- Bob이 이 참조를 제시.
- 검증: 서비스 제공자가 그 컨트랙트에 `isValid(0xD1, "결제", 요청금액)`을 호출 → **컨트랙트가 온체인 정보로 직접 유효성 판정**(유효 여부·사유 반환).
- 별도의 사용자 서명 증표가 없다. 등록 시점의 사용자 승인·서명이 이미 온체인 상태에 반영되어 있기 때문.

## 3. 위임 토큰 방식 (§5.2.3)

Alice **서명이 담긴 경량 토큰**(JWT 유사)을 발급한다.

```
token = {위임ID:0xD1, agent:Bob, scope:결제}.<Alice 서명>
```

- Bob이 토큰을 제시.
- 검증: ① Alice 공개키로 **토큰 서명 검증** → ② 위임 ID로 **온체인 권한위임정보 조회·대조**. (VC와 유사하나 형식이 가볍다.)

## 4. 일회용키 방식 (§5.2.4)

발급자가 이 위임 전용의 **임시 프라이빗키(1회용)** 를 Bob에게 발급한다.

```
위임장 = 임시 프라이빗키 (위임 0xD1에 연결, 1회용)
```

- Bob이 그 키로 서비스 이용 요청에 **서명**.
- 검증: 서비스 제공자가 DID 레지스트리에서 그 위임에 연결된 임시 공개키를 얻어 **에이전트 서명 검증** + 위임 ID로 온체인 대조. 일회용이라 재사용 공격을 차단.

## "레지스트리 어드레스 + 위임 ID"는 네 가지 모두 해당하는가

| 방식 | 위임장(증표)의 실체 | 위임 ID | 레지스트리 어드레스 |
|---|---|---|---|
| VC | Alice 서명 자격증명(오프체인) | 증표에 포함 | 검증 시 조회에만 사용 |
| SC 어드레스 | (레지스트리 주소 + 위임ID) 참조 | 증표에 포함 | **증표에 직접 포함** |
| 위임 토큰 | Alice 서명 토큰(오프체인) | 증표에 포함 | 검증 시 조회에만 사용 |
| 일회용키 | 임시 프라이빗키 | 키에 연결 | 검증 시 조회에만 사용 |

- **위임 ID**: 네 가지 **모두 공통** (온체인 권한위임정보의 열쇠).
- **레지스트리 컨트랙트 어드레스**: 검증 시 온체인 조회가 필요하다는 점은 공통이나, **어드레스를 위임장 증표에 직접 넣는 것은 SC 방식의 특징**이다. 나머지 세 방식은 서명 증표(VC/토큰/키) + 위임 ID로 조회하며, 레지스트리는 시스템에 알려진 컨트랙트를 사용한다.

## 핵심 요약

- **권한 내용(권한위임정보)은 어느 방식에서든 항상 온체인(위임 레지스트리)에 등록된다.**
- 네 가지는 "그 위임을 증명하는 **증표**"의 형태 차이일 뿐이다.
- **SC 어드레스 방식**만 증표가 온체인 위치를 직접 가리키는 **참조형**이고, **VC·토큰·일회용키**는 사용자 서명이 담긴 증표를 오프체인으로 전달하는 형태이다(검증 시 위임 ID로 온체인 정보와 대조).
- 자기완결/참조의 구분은 "정보 유무"가 아니라 "증표 전달 방식"의 차이다.
